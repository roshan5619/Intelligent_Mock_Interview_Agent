01

Overview & user journey

What we built, who it's for, and how it feels.
Q. What is IPHIPI in one sentence?
A multimodal, agentic AI mock-interview platform that reads a candidate's resume, infers the roles they can realistically land, and conducts a live video + audio interview with adaptive questioning and explainable scoring.
Why it matters

Senior professionals lack rigorous, role-appropriate practice; static question banks don't adapt; generic LLM chats can't read body language or vocal cues. We close that gap on free SOTA models.

Q. Who is the target user?
A senior professional (10-15+ years) preparing for a technical or leadership interview at a peer company. The orchestrator, prompts, and scoring are calibrated to that seniority level.
Reasoning

The brief explicitly named a 15-year senior candidate. Calibrating to that audience changed everything: the orchestrator opens with peer-level framing, not quiz-style trivia, and the technical evaluator reserves 0.9+ for genuinely outstanding answers.

Q. Walk through the end-to-end user journey.
  • Land on the IPHIPI marketing site → browse careers or upload a resume on /match-me.
  • The Context Understanding agent extracts a structured profile and infers target roles.
  • JD Match scores every IPHIPI role with explainable sub-scores (semantic + skill overlap + seniority).
  • Pick a role → apply → see the fit ring + breakdown.
  • Click Start mock interview. The pre-flight requests camera + mic, previews the agenda, and calibrates the eye-contact baseline.
  • The interview runs hands-free: VAD auto-detects when the candidate speaks, transcribes live, and auto-submits ~0.9 s after they pause.
  • Each turn is scored in parallel by Audio, Visual, and Technical agents; the Orchestrator decides the next question and adapts difficulty.
  • End → Agent 6 generates a structured report with per-dimension scores, evidence quotes, and concrete next steps.
Code: app/page.tsx, app/match-me/, app/apply/[slug]/page.tsx, app/interview/[sessionId]/page.tsx
Q. What does "agentic AI" mean here? Why not a single LLM chain?
Six specialized agents observe, decide, and adapt in concert: one parses, one drives the conversation, one hears, one sees, one grades, one coaches. Each is a typed module with a single responsibility.
Reasoning

One mega-prompt would be cheaper to write but impossible to debug, calibrate, or replace. Decoupled agents let us swap providers per task (Gemini for PDFs, Groq for reasoning), score-test each one in isolation, and keep the technical evaluator deterministic-feeling without compromising the orchestrator's warmth.

Q. What does "multimodal" mean in this product?
The interview captures three input streams in parallel — webcam video, microphone audio, and live transcript — and produces four output dimensions: technical, communication, confidence, engagement.
Reasoning

Real interviews are won and lost on body language and vocal cues, not just words. Sampling all three streams lets the report say "vocal confidence dipped on the database-sharding question; pitch flattened and pauses lengthened" — coaching that's impossible from text alone.

Q. What's special about the demo experience versus a normal AI chat?
It's hands-free. No mic button, no Send button. Voice-activity detection auto-starts the turn ~200 ms after the candidate begins talking and auto-submits ~900 ms after they stop. The candidate just speaks naturally; the system feels like a conversation, not a form.
Code: lib/voice/audio-analyzer.ts (VAD), components/iphipi/interview-workspace.tsx
Q. What's the scoring philosophy?
Every score ships with evidence. The match score has matched skills + gaps + a one-paragraph rationale grounded in the deterministic numbers. Every per-turn evaluation has a quoted fragment from the transcript. The final report's improvement bullets each cite a specific moment.
Reasoning

"You scored 71" is useless. "You scored 71 because in turn 4 you led with the technology stack rather than the constraint it solved" is actionable. We made evidence-quoting a hard rule in every agent's system prompt.

Q. What does success look like for the demo?
A senior engineer uploads their real resume, sees the top fit role surface with believable rationale, takes a 6-turn live interview, and walks away with a report that includes one improvement they'd actually apply tomorrow.
02

High-level architecture

Where every layer lives and why.
Q. Describe the architecture in three layers.
  • Browser: handles all multimodal capture + ML — MediaStream, Web Audio, Web Speech, MediaPipe Tasks. Raw video and audio never leave the device.
  • Vercel server: Next.js 16 App Router on the Node runtime. Hosts marketing pages, the apply flow, and four interview API routes. Six agent modules are pure functions called from the routes.
  • External services: Groq Cloud (Llama 3.3 70B), Google Gemini (PDF + embeddings), Turso (libSQL DB), Vercel Blob (PDF storage). Each is reachable from Vercel functions; none requires a tunnel or a laptop.
See: docs/ARCHITECTURE.md
Q. Why split multimodal capture into the browser?
Three reasons: privacy (raw frames never leave the device), bandwidth (~2 KB of metric JSON per turn instead of MB/s of video), and the fact that browser-native ML (MediaPipe Tasks WASM) is genuinely fast and free.
Reasoning

Hosting CV models server-side would require GPUs, network throughput for video, and a privacy story we'd need to defend. Browser-side MediaPipe sidesteps all three.

Q. Why Next.js full-stack on Vercel rather than React + a separate Python backend?
Single repo, single deploy, single set of env vars, single CDN. Server actions and API routes live next to the pages that call them. We get edge-CDN'd marketing pages and Node-runtime API routes from the same project.
Reasoning

For a 2-day prototype the integration tax of a separate Python service was the dominant cost. Next.js + Groq SDK / Gemini SDK gave us full LLM access without leaving Node.

Q. Why Turso for the database?
It's libSQL — a managed, SQLite-compatible service with a generous free tier. Same SQL, same query patterns, drops into Postgres later because we use only standard SQL.
Reasoning

Postgres on Neon would also work; Turso wins on local-dev parity (the same connection string can point at a local file). One DAL covers both prod and dev.

Code: lib/storage/db.ts, db/schema.sql
Q. Why Vercel Blob for resumes? Why private access?
It's the lowest-friction managed object store integrated with Vercel. We use access:'private' because resumes are sensitive PDFs; the URL is internal and the server reads them back via head() with a token to obtain a signed download URL.
Code: lib/storage/blob.ts
Q. Walk through what happens during a single turn.
  • Browser flushes AudioMetrics + VisualMetrics for the just-spoken turn.
  • POST /api/interview/turn persists the candidate turn.
  • Three agents fire in parallel: Audio scoring (Agent 3, LLM), Technical scoring (Agent 5, LLM), Visual scoring (Agent 4, deterministic math).
  • All per-dimension agent_evaluations rows are persisted.
  • The Orchestrator (Agent 2) runs with profile + agenda + transcript + latest metrics + 2-turn trends; adaptive heuristics may force drop_difficulty, ramp_difficulty, or wrap_up.
  • The next interviewer turn is persisted and returned. Browser speaks it via TTS, then the cycle repeats.
Code: app/api/interview/turn/route.ts
Q. What's deployed where?
All Next.js routes (static + dynamic) are on Vercel. Turso runs in Turso's edge regions. Vercel Blob is in Vercel's edge storage. Groq + Gemini are reached through their public APIs from the Vercel function runtime. There is no local laptop in the production path.
Q. How is the codebase organized?
  • app/ — pages and API routes (App Router). Routes contain wiring only; no domain logic.
  • lib/agents/ — one file per agent (six total) plus the agenda planner.
  • lib/prompts/ — versioned .md system prompts, one per agent.
  • lib/llm/ — multi-provider router with Groq, Gemini, and Ollama adapters.
  • lib/voice/, lib/vision/ — browser-side ML wrappers.
  • lib/storage/, lib/auth/, lib/matching/, lib/embeddings/ — supporting domains.
  • components/iphipi/ — branded composites (workspace, score ring, forms).
03

Tech-stack decisions

Why each tool was chosen, and what we declined.
Q. Why Groq Llama 3.3 70B as the primary reasoner?
It's the fastest hosted LLM today (~500 tok/s), it's near-frontier on general reasoning benchmarks, and the free tier is comfortable (30 RPM, 14,400 RPD). The first-token latency on the Orchestrator drops to ~300 ms — the difference between feeling sluggish and feeling natural.
Reasoning

Speed mattered more than the marginal quality jump from a 405B model. With six agents per turn, sub-second first-token latency is what makes the conversation feel alive.

Q. Why Gemini for PDFs and embeddings?
Gemini natively understands PDFs — no pdf-parse step needed. generateFromPdf() takes the inline base64 PDF + a JSON-mode prompt and returns the structured profile in one call. Plus Gemini's embeddings (gemini-embedding-001) are free and 768-dim.
Code: lib/llm/providers/gemini.ts
Q. What is the multi-provider router and why does it exist?
lib/llm/client.ts exposes one entry point — generate(), generateStream(), embed(), generateFromPdf() — and internally tries providers in a fallback chain (Groq → Gemini → Ollama). Each provider self-reports availability based on whether its env key is set.
Reasoning

A demo cannot hard-fail when one provider's free tier hits its rate limit. The router transparently retries on the next provider, so the worst case is one extra second of latency, not a broken demo.

Q. Why MediaPipe and not, say, a vision LLM for the body-language analysis?
MediaPipe Tasks is pretrained, free, runs in WASM at 15-30 FPS in the browser, and gives exact, deterministic landmarks. A vision LLM would be 1000× slower per frame and non-deterministic for tasks like "where is the nose tip".
Reasoning

The brief specifically said: prefer pretrained CV over LLMs. We honored it because for "is the candidate looking at the camera" you want exact pixel coordinates, not a sentence.

Q. Why Web Speech + Web Audio rather than Deepgram + Whisper?
Cost (free vs paid), infra (zero vs one more vendor), latency (in-browser vs network round-trip). Trade-off: Web Speech is Chrome/Edge/Safari only, and STT quality is lower than Deepgram. The "Type instead" toggle is the always-available fallback.
Q. Why TypeScript strict and zod schemas?
LLM outputs are a known source of shape drift. Every agent's output is parsed and zod-validated; a schema mismatch raises a typed error, not a silent wrong field downstream.
Code: lib/agents/context-understanding.ts ContextProfileSchema
Q. Why no auth in the prototype?
The candidate identity is a signed HMAC cookie — a JSON payload + HMAC-SHA256 signature keyed by HMAC_SECRET. Magic-link via Supabase Auth is queued for v2. The prototype's ownership checks (cookie's candidate ID matches the application/session) are sufficient for hackathon scope.
Code: lib/auth/candidate-token.ts
Q. What went into keeping costs at zero?
Groq + Gemini free tiers, Vercel Hobby, Turso free, Vercel Blob 1 GB free. The total recurring cost is $0. The only paid scenarios are scale (rate limits) or v2 features (Deepgram, Claude Sonnet).
04

Agent 1 · Context Understanding Module

Resume → ContextProfile. The starting point for every other agent.
Q. What does Agent 1 do?
It takes a resume (PDF or text) and produces a ContextProfile: skills, years, roles, projects, education, certs, domains, seniority signals, and a ranked list of inferred target roles with rationale and matched evidence.
Code: lib/agents/context-understanding.ts · Prompt: lib/prompts/01_context_understanding.md
Q. Walk through parseResumePdf() step by step.
  • Try Gemini's native PDF understanding: gemini.generateFromPdf(pdf, prompt, {json:true}) — Gemini accepts the inline base64 PDF and the system prompt together.
  • If Gemini fails (rate-limit, network), fall back to pdf-parse for text extraction, then route through parseResumeText() which uses the multi-provider router (Groq, then Gemini-text, then Ollama).
  • The raw response is stripped of markdown fences (some providers wrap JSON despite instructions) and zod-validated against ContextProfileSchema.
  • On schema mismatch, throw ContextParseError with the raw output for debugging.
Reasoning

Gemini PDF avoids extraction loss (resumes have columns, headers, spacing the regex parsers butcher). The text-fallback exists because Gemini's free tier has tight RPM limits — we cannot allow a quota error to break apply.

Q. What's in ContextProfile and why those fields?
  • skills[] — drives skill-overlap matching.
  • years_total — drives seniority fit.
  • roles[], projects[], education[], certs[] — provide quotable evidence for the orchestrator and the report.
  • domains[] — broad industry signals (fintech, ML infra, …).
  • seniority_signals[] — phrases like "led team of 6" used by the orchestrator to set baseline difficulty.
  • inferred_roles[] — ranked list with confidence + rationale + matched evidence; powers /match-me.
Q. How is role inference done?
The system prompt provides a closed taxonomy of roles (Backend, Frontend, Data Analyst, DevOps, QA, Product, Mobile, ML, SRE, Security, Eng Manager, Other). The LLM is instructed to rank 2-5 likely target roles, attaching a 0-1 confidence and 2-4 evidence quotes per role.
Reasoning

Closed taxonomy prevents the model from inventing exotic roles like "Distributed Quantum Engineer" that don't exist in our jobs table.

Q. Why a separate prompt file rather than an inline string?
Prompts live as .md files in lib/prompts/. They're loaded once and cached. Markdown is diff-friendly in PRs, easier to read, and trivially portable to a future prompt-management UI.
Code: lib/prompts/index.ts
Q. What hard rules does the prompt enforce?
JSON only (no prose, no fences). Every field required. Never invent skills the candidate doesn't claim. If the input doesn't look like a resume at all, return all-empty arrays + a single Other-role at confidence 0.
Reasoning

The "never invent" rule prevents the most dangerous LLM failure mode for HR tooling: false skill attribution.

Q. How is this used downstream?
ContextProfile is persisted on applications.context_profile_json and read by:
  • JD Match — for embedding similarity, skill overlap, seniority fit.
  • Agenda planner — for project deep-dives and gap probes.
  • Orchestrator — every turn includes an abbreviated profile for question generation.
  • Technical Eval — abbreviated profile lets the agent flag contradictions vs the resume.
  • Feedback & Coaching — final report cites resume-grounded evidence.
Q. What's the latency of Agent 1?
~10-20 seconds for a typical 1-2 page resume on Gemini 2.0 Flash, including PDF parsing + LLM inference + JSON validation.
Q. How is failure surfaced to the user?
The apply form runs a perceived-progress trail (uploading → parsing → scoring). On error, an inline red box shows the message ("invalid PDF", "rate-limited", etc). The candidate page also shows a "Scoring still in progress" placeholder if the breakdown row is null.
Code: components/iphipi/apply-form.tsx

Agent 2 · Interview Orchestrator

The conversational driver. Decides every next interviewer turn.
Q. What's the orchestrator's job?
Look at the candidate's profile, the agenda, the transcript so far, the latest multimodal metrics, and the time budget — and emit one OrchestratorDecision: an intent, a focus area, a difficulty, a question style, and the actual next question the candidate hears.
Code: lib/agents/orchestrator.ts · Prompt: lib/prompts/02_orchestrator.md
Q. What inputs does it consume per turn?
An abbreviated ContextProfile, the target role + must-haves, the remaining agenda, the last 6 turns of transcript, the latest audio + visual + technical metrics, the 2-turn trends for confidence + correctness, and the time budget remaining.
Q. What does OrchestratorDecision look like?
{
  "intent": "probe_deeper" | "switch_topic" | "drop_difficulty"
          | "ramp_difficulty" | "clarify" | "encourage" | "wrap_up",
  "target_focus_area": string,
  "difficulty": 1 | 2 | 3 | 4 | 5,
  "question_style": "open_ended" | "scenario" | "system_design"
                  | "behavioral_star" | "trivia",
  "next_question": string  // ≤ ~50 words
}
Q. How is the LLM constrained to always return valid JSON?
Three things stack: (1) Groq's response_format: { type: 'json_object' }, (2) the system prompt's hard rule "JSON only, no fences", (3) zod validation server-side. If any layer fails the others catch it.
Q. How does it adapt to the candidate?
The LLM is given the trends, but we layer hard heuristics on top:
  • confidence_trend shows 2 consecutive turns < 0.4 → force drop_difficulty and prepend warm encouragement to the question.
  • correctness_trend shows 2 consecutive turns > 0.85 → force ramp_difficulty.
  • Time budget below 2 minutes → force wrap_up.
Reasoning

Asking a 70B LLM to "be empathetic about confidence dips" is hopeful. Forcing the intent in code is reliable. The LLM still writes the actual sentence, but the policy is deterministic.

Code: lib/agents/orchestrator.ts applyHeuristics()
Q. Walk through buildAgenda().
A heuristic planner — no LLM call — that builds 5-7 agenda items deterministically:
  • 3 core_skill items, one per top must-have of the job.
  • 2 project_deep_dive items from the candidate's top projects.
  • 1 behavioral item, always.
  • 1 gap_probe if the resume tokens don't contain a must-have keyword.
Reasoning

Asking an LLM to plan the agenda would add latency and variance for no quality gain — the heuristic is good enough and 100% reproducible per (resume, job) pair.

Code: lib/agents/agenda.ts
Q. How does the orchestrator stay grounded in the resume?
abbreviateProfile() trims the profile to the orchestrator's actual context window: top 20 skills, 5 roles, 4 projects, 5 seniority signals, top 3 inferred roles. The full profile is in DB; the orchestrator only sees what's relevant for question framing.
Q. Why no streaming for the orchestrator?
Each Orchestrator output is ~50 words (~100 tokens). On Groq that's ~250 ms total. Streaming adds complexity for a marginal perceived-latency win. We do speak the response via TTS the moment the JSON arrives, which is the user-facing latency that matters.
Q. How is the conversation persisted?
Every turn (agent or candidate) becomes one row in interview_turns. Per-turn metric blobs are stored as JSON columns. agent_evaluations rows fan out per dimension. The session is fully resumable from (session_id) alone.
Q. What guardrails prevent the orchestrator from rambling?
The prompt caps next_question at ~50 words and forbids stacking three questions in one turn. The system role enforces a senior, peer-level tone. The model temperature is 0.7 — warm but not chaotic.

Agent 3 · Audio Intelligence

Hears confidence and clarity from voice + transcript.
Q. What does Agent 3 produce?
Two scores per turn — confidence (0-1) and clarity (0-1) — plus a one-sentence evidence string and a one-sentence signals summary.
Code: lib/agents/audio-intelligence.ts · Prompt: lib/prompts/03_audio_intelligence.md
Q. How is audio captured in the browser?
AudioAnalyzer wires a MediaStreamAudioSourceNode into an AnalyserNode with fftSize=2048, then samples getFloatTimeDomainData() every ~50 ms.
Code: lib/voice/audio-analyzer.ts
Q. What signals does the analyzer compute per turn?
  • RMS mean + variance: volume envelope.
  • Pitch mean + variance: via simple time-domain autocorrelation; flat F0 = monotone.
  • Pause ratio + silence pct: windows below the silence threshold.
  • WPM: words from the transcript divided by turn duration.
  • Fillers per minute: counts of "um/uh/like/you know" in the transcript.
Q. How is voice activity detection (VAD) implemented?
Two-state machine on the same RMS samples: NOT_SPEAKING vs SPEAKING. We require ~200 ms of sustained energy above 0.030 to fire onSpeechStart, and ~900 ms of sustained silence to fire onSpeechEnd. Both events are surfaced as callbacks the workspace uses to drive the UI state machine.
Reasoning

0.030 is a moderate floor that catches quieter speech without false-triggering on room hum. 900 ms is short enough to feel snappy, long enough that mid-sentence breath pauses don't terminate a turn.

Q. Why pitch via autocorrelation rather than FFT?
Time-domain autocorrelation is computationally cheap, deterministic, and good enough for human voice (60-400 Hz). FFT-based pitch detection is more accurate but overkill for our use case — we only need mean + variance, not exact F0 contours.
Q. Why does the LLM rather than a formula assign the final scores?
The metrics are inputs; the rubric requires interpretation. "WPM=180 with high pitch variance" is high confidence in one cultural context, not in another. The LLM also reads the transcript itself for hedging language ("I think maybe sort of") which a formula misses.
Reasoning

We get the best of both: deterministic numbers that can't be hallucinated + a calibrated linguistic interpretation.

Q. Why echoCancellation and noiseSuppression on the mic stream?
The TTS speaks the AI's question through the system speakers. Without echo cancellation that audio would loop back into the mic and trigger VAD as if the candidate were speaking. echoCancellation: true in getUserMedia filters it.
Q. Why start SpeechRecognition before VAD fires?
Web Speech API takes 200-500 ms to actually start capturing after .start(). If we waited for VAD to fire then started the recognizer, we'd miss the first word(s) of every answer. The recognizer runs throughout the listening + recording states; VAD only signals when to flush.
Code: components/iphipi/interview-workspace.tsx startRecognizer()

Agent 4 · Visual Intelligence

Sees engagement and stress without ever sending video off-device.
Q. What does Agent 4 do?
Per-frame, runs MediaPipe FaceLandmarker (478 face points + blendshapes) and PoseLandmarker (33 body keypoints) to derive: eye-contact ratio, head-pose stability, posture score, smile/brow/jaw blendshapes, and blink rate. Per-turn, it produces a VisualMetrics blob.
Code: lib/vision/metrics-aggregator.ts, lib/agents/visual-intelligence.ts
Q. Why is the server side deterministic math instead of an LLM?
The brief specifically asked for pretrained CV. The metrics are already structured numbers — feeding them to an LLM to compute weighted averages is wasteful. We use formulas:
engagement = 0.5
           + 0.25 × (eye_contact_ratio - 0.5)
           + 0.15 × (smile + brow_raise)
           + 0.10 × (head_pose_stability - 0.5)

stress     = 0.5 × jaw_tension
           + 0.3 × (1 - eye_contact_ratio)
           + 0.2 × (1 - head_pose_stability)
Reasoning

Cheap, deterministic, always available. The Feedback agent later reads these scores and writes the narrative interpretation, which is the right place for the LLM to add value.

Q. How is eye contact detected?
We track landmark 1 (nose tip). During the 30-second warmup we capture the candidate's natural-position nose X as a baseline. Per-frame, we count the frame as "eye contact" if the nose is within ±0.08 normalized units of baseline AND in the central X band (0.4-0.6). The ratio over the turn becomes eye_contact_ratio.
Reasoning

We don't have iris-gaze precision but we don't need it. Head-orientation as a proxy is reliable enough for "is the candidate looking forward at the screen".

Q. How is posture computed?
From PoseLandmarker landmarks 11/12 (shoulders) and 0 (nose). We measure shoulder-Y symmetry (collapsed = leaning) and head-over-shoulder centering (offset = slouching/turning). Weighted: 50% symmetry, 50% centering.
Q. What blendshapes drive the expression signals?
  • Smile: mouthSmileLeft/Right minus 0.5× mouthFrownLeft/Right.
  • Brow raise: max of browInnerUp, browOuterUpLeft/Right.
  • Jaw tension: max of jawOpen, mouthPressLeft/Right.
  • Blink: peak-counting on eyeBlinkLeft/Right > 0.55.
Q. How does the live face mesh overlay work?
A <canvas> is layered on top of the <video> with the same dimensions. After each MediaPipe detection (~15 FPS), we draw all 478 landmarks as 1.1-pixel brand-colored dots. Visible proof to the candidate that the vision model is running on their face right now.
Code: components/iphipi/interview-workspace.tsx drawFaceMesh()
Q. How do the live gauges update?
VisionMetricsAggregator exposes snapshot() — a running average that doesn't reset state. The MediaPipe loop calls it every 250 ms; the workspace renders Eye-contact / Engagement / Posture bars below the cam.
Q. What's the privacy story?
Raw video frames never leave the browser. Only the aggregated VisualMetrics JSON (~2 KB) is sent per turn. The "Local only" badge in the workspace cam corner makes this visible.
08

Agent 5 · Technical Evaluation Engine

Grades each answer against the question with evidence quotes.
Q. What does Agent 5 score per answer?
Four 0-1 dimensions: correctness, depth, specificity, concept_coverage. Plus a mandatory evidence_quote (must be a substring of the answer) and a flags array.
Code: lib/agents/technical-evaluation.ts · Prompt: lib/prompts/05_technical_evaluation.md
Q. What flags does it produce?
  • hallucination — candidate states something specific and false.
  • contradiction_with_resume — answer contradicts a resume claim.
  • off_topic — answer doesn't engage the question.
  • insufficient_detail — too short to score.
Q. How is calibration enforced?
The prompt instructs explicitly: "most senior-engineer answers fall in 0.5-0.8; reserve 0.9+ for genuinely outstanding answers". This anchors the model so a competent answer scores ~0.7 rather than 0.95.
Q. How is the evidence quote enforced?
The prompt requires the quote to be a substring of the candidate's answer; the system promises an empty string if none fits. Downstream the report cites quotes — if they were invented we'd lose trust.
Q. Why is "concept coverage" separate from correctness?
A candidate can be correct but shallow (covers 1 of 5 expected concepts well) or wide but inaccurate (touches all 5 with errors). Treating coverage as its own dimension surfaces both failure modes in the report.
Q. How is the previous interviewer turn linked to this evaluation?
In /api/interview/turn, before persisting the candidate turn, we fetch the most recent agent turn from the session. That turn's content is passed as question to the technical evaluator. The expected concepts can later be injected by the orchestrator (currently inferred from the question by the LLM).
Q. What happens if the candidate answers "I don't know"?
Per the prompt, all four dimensions return 0.1 with flags:["insufficient_detail"]. We don't penalize at 0.0 — the candidate knew enough to say they didn't know, which is a real (small) signal.
09

Agent 6 · Feedback & Coaching

Writes the final report. Runs once at end of session.
Q. What does Agent 6 produce?
A structured Report: a 2-sentence summary, four 0-100 dimension scores plus an overall, four markdown sections (strengths, improvements, behavioral insights, next steps).
Code: lib/agents/feedback-coaching.ts · Prompt: lib/prompts/06_feedback_coaching.md
Q. What does it consume?
The full transcript, the candidate's profile, the target job, and every agent_evaluations row from the session — pre-aggregated into per-dimension averages, "low confidence moments" (turns with confidence < 0.4), and "stress peaks" (stress > 0.7).
Q. How does pre-aggregation work?
aggregateMetrics() walks all evaluations, groups by dimension, computes averages, and joins low-confidence and stress-peak turns back to their question stems. The LLM gets a compact JSON of aggregates + the top-12 most-extreme moments — manageable context, full evidence base.
Q. Why is overall recomputed server-side after the LLM returns?
The prompt documents the formula 0.35×technical + 0.30×communication + 0.20×confidence + 0.15×engagement. We recompute it server-side from the LLM-returned dimension scores so the LLM cannot drift on the weighting. Trust the LLM for narrative; trust code for arithmetic.
Q. What style rules does the prompt enforce?
  • Specific over generic ("practice STAR" → forbidden; "when asked about cross-team migration, you led with stack rather than the constraint" → required).
  • Quote the candidate. Every strength and improvement cites a moment.
  • Honest, not performative — calibrated 70-85 for a senior who held their own; 90+ rare.
  • Read audio + visual together (a confidence dip + posture slump + jaw tension = stress signal).
Q. How is the report rendered?
Server-rendered page at /interview/[sessionId]/report. A custom minimal markdown renderer handles headings, paragraphs, bullets, and bold. The score ring + per-dimension bars use the same SVG component as the apply page.
Code: app/interview/[sessionId]/report/page.tsx

Per-turn data flow

How the six agents coordinate without blocking the conversation.
Q. Walk through one full turn end-to-end.
  • Candidate stops speaking → VAD fires onSpeechEnd in the browser.
  • Workspace stops the recognizer, waits 200 ms for the last final result, flushes AudioMetrics + VisualMetrics, optimistically appends the candidate turn.
  • POST /api/interview/turn with {sessionId, candidateText, audioMetrics, visualMetrics}.
  • Server persists the candidate turn.
  • In parallel: Agent 3 (audio LLM scoring), Agent 5 (technical LLM scoring), Agent 4 (deterministic CV math).
  • All per-dimension agent_evaluations rows are persisted.
  • Server builds 2-turn confidence + correctness trends.
  • Agent 2 (Orchestrator) runs with profile + agenda + recent turns + latest metrics + trends + time budget. Adaptive heuristics may override the intent.
  • New interviewer turn is persisted and returned in the JSON response.
  • Browser appends the agent turn, updates the gauges, speaks the question via TTS, then transitions back to listening.
Q. Why parallel scoring?
Three LLM calls + one CV math call would total ~6 s sequentially on Groq. Promise.all makes them ~2 s. The candidate-perceived latency is dominated by the orchestrator's call after — not the evaluators.
Q. What if one of the parallel scorers fails?
Each is wrapped in .catch(err => null) with a console warn. The orchestrator gracefully degrades — its prompt accepts n/a for any metric. The report's aggregator also tolerates missing rows.
Code: app/api/interview/turn/route.ts
Q. Why are turn rows persisted before evaluations?
If anything fails afterward, we still have the transcript. The session is resumable from (session_id) and any incomplete evaluations don't block the report from running with what's there.
Q. What schema-level constraints support resumability?
interview_turns has UNIQUE (session_id, turn_index) implicitly enforced by us; reports.session_id is UNIQUE so we can UPSERT rather than duplicate. ULIDs sort lexicographically by time so we can replay the session in the order it happened.

Privacy, security, scale

What we got right at small scale and what changes at large scale.
Q. What never leaves the browser?
Raw video frames and raw audio buffers. Only the per-turn aggregated metric JSONs (~2 KB each) reach the server. The candidate sees a "Local only" badge in the cam corner reinforcing this.
Q. How are resumes protected?
Vercel Blob with access:'private'. Server-side reads use head() with the BLOB_READ_WRITE_TOKEN to obtain a signed download URL. The blob URL is never exposed to the client.
Q. How is the candidate cookie tamper-proof?
Format: base64url(payload).base64url(hmac), where the HMAC-SHA256 is keyed by HMAC_SECRET over the base64url-encoded payload. Verification uses timingSafeEqual. Forgery requires the secret.
Code: lib/auth/candidate-token.ts
Q. What ownership checks are enforced?
Every protected route verifies the cookie's candidate ID matches the application/session being acted on:
  • /candidate/[id] — server checks application.candidate_id equals the cookie's claim.
  • /api/interview/start|turn|end — same check via the session's parent application.
  • /match-me/results/[runId] — checks role_match_runs.candidate_id.
Q. How does the system handle rate-limited LLMs?
The router falls back transparently — Groq → Gemini → Ollama. A user-facing "Live AI offline — retrying" banner only appears if every provider fails. The router logs the provider and duration for every successful call.
Q. What's the international scaling plan?
  • Vercel edge for static + per-region serverless functions.
  • Turso has multi-region read replicas on the paid tier; we already use libSQL primitives that work with replicas.
  • Move the heavy LLM workload to Claude Sonnet 4.6 for better reasoning at higher latency tolerance — the orchestrator becomes 1-2 s slower but report quality jumps.
  • Add Upstash Redis for token-bucket rate limiting per-user + per-IP on the apply + interview-start endpoints.
Q. What's the worst-case failure for a live demo?
Both Groq and Gemini being down simultaneously. We mitigate with the OLLAMA_BASE_URL escape hatch — if a presenter has Ollama running, the router falls back to it. The dev console logs every fallback so we always know what fired.
Q. Are there any compliance considerations for v2?
For paid customers we'd add: GDPR consent on resume upload, retention policy (auto-delete blobs after 30 days), audit log of agent decisions, and an opt-out path for using transcripts as training data. The interfaces in lib/storage/ were designed to make these single-file additions, not rewrites.

Deployment & ops

How this gets to production and stays there.
Q. Where is it deployed?
Vercel — production URL https://iphpi-hackthon.vercel.app. The repo is connected to the project so every push to main triggers an auto-deploy.
Q. What's the CI/CD pipeline?
Push to GitHub → Vercel webhook → Vercel build (turbopack production build, page-data collection, route generation) → atomic deploy to a fresh URL → alias to iphpi-hackthon.vercel.app. Average build time ~45 s.
Q. What's the one-command setup story?
npm run setup applies the schema (idempotent CREATE TABLE IF NOT EXISTS) and seeds the 6 IPHIPI roles. Falls back to a local SQLite file in ./data/ if Turso env vars aren't set, so a developer can clone-and-run.
Code: scripts/setup.ts
Q. How are secrets managed?
Six env vars live in the Vercel dashboard's Environment Variables panel and are never committed (.env.local is gitignored). Local dev uses .env.local. scripts/check-env.ts reports which keys are set without ever printing values.
Q. What's the rollback story?
Vercel keeps every previous deploy; promoting an older one is one click in the dashboard. The DB schema is purely additive (CREATE TABLE IF NOT EXISTS, no destructive migrations), so an older app version never crashes against a newer DB.
Q. What does npm run check:samples verify?
Runs Agent 1 against samples/resumes/senior-backend.txt, then JD-Match against the staff-backend role, asserting structural validity (≥5 skills, years_total≥10, score≥50, evidence quote present). Outputs are non-deterministic so we test shape, not exact values.
Code: scripts/check-samples.ts
Q. What's the demo-day playbook?
  • Use Chrome (latest). Wired ethernet preferred over Wi-Fi.
  • Open the live URL → upload samples/resumes/senior-backend.txt as a PDF on /match-me.
  • Watch the ~25 s ranking → click the top role → see the fit ring + breakdown.
  • Click Start mock interview → grant camera/mic → answer 3-4 turns.
  • Click End & see report → demo the per-dimension scores + coaching.
See: docs/RUNBOOK.md
Q. What's left for v2?
Magic-link auth + returning-candidate dashboard, Deepgram + ElevenLabs for cross-browser broadcast-quality voice, Claude Sonnet 4.6 as a higher-quality reasoning option, agent-decision audit logs, eval harness with golden interviews + LLM-as-judge regression tests, multi-tenant scaling + rate limiting.
Q. What can go wrong during a real demo, and what's the mitigation?
  • Groq rate limit: router falls to Gemini; banner shows only if both fail.
  • Camera permission denied: pre-flight surfaces a clear red error with the OS-level message.
  • Mic captures TTS as user voice: mitigated by echoCancellation:true on the input stream.
  • Slow inference: async non-blocking evaluators keep candidate-facing latency to one LLM call per turn.
  • MediaPipe model fetch blocked: warmup view stays visible with a clear loading state; the workspace doesn't enter live phase until models are ready.
